### 🟡 P1 — AI opener infinite loop (the 10-14 call)

```
AI  : Handiwork service desk. What's the issue?
Cust: Hi. Um, do you guys install TV now?
AI  : What's the issue?      ← completely ignores that the customer already stated their need
Cust: Do you install TV now?
AI  : What's the issue?      ← keeps repeating
Cust: What kind of work do you offer
AI  : What's the issue?      ← third repetition
```

Root cause (corrected after the deep dive on 2026-10-29 — it was **not** the previously suspected "flat intonation on the period"): **the prompt hard-coded the opener as a script**.

```
## 3-turn flow (keep it tight)

### Turn 1 — Identify + zip
You: "What's the issue."              ← this line is a literal script
Customer: "I have a kitchen sink that's leaking, I'm in 77005"
```

Two problems stack on top of each other:
1. `You: "What's the issue."` is a **hard-coded line in the prompt**, exactly duplicating Vapi's `firstMessage` — the model now holds a "universal repeat key".
2. The customer's line in the script **states a problem** ("my faucet is leaking"). When the customer **asks a question** ("do you install TVs"), it does not match that shape, so the model thinks Turn 1 is not finished yet and recites the script's first line again — and that is the only line it knows.

So no matter how clearly the customer states their need, it makes no difference: **the interrogative form has no matching response path** (the FAQ and service list at the time contained no entries of the "do you do X" kind).

Reproduction evidence (running the same conversation with the old prompt from back then, against the live OpenAI):
```
customer: Hi. Um, do you guys install TV now?
AI:       What's the issue?      ← word-for-word identical to the live incident
customer: Do you install TV now?
AI:       What's the issue?
customer: What kind of work do you offer
AI:       What's the issue?
```
Note that this is **probabilistic**: with the same model and the same temperature 0.2, the old prompt sometimes reproduces and sometimes works fine — which is why it could quietly live for two weeks.

**Fix** (pushed to Vapi, confirmed by reading it back: v36 / 15370 characters):
- **Delete** the `You: "What's the issue."` line from the prompt, and state that "the opener is already covered by the greeting, it is not your line"
- Add a new **"Answer the question they asked"** section: **never answer a question with a question**, answer first, then ask for the ZIP code
- Add a new **"Service quick answers"** section: 14 ready-made one-line answers to "do you do X" (TV / furniture / plumbing / electrical / AC / painting / drywall repair / car washing / fences / curtains / hanging pictures / smart home / roofing / what kind of work do you do")
- Add a rule to Hard rules: "Never answer a customer's question with another question"
- `firstMessage` → `"Handy Works service desk. What's the issue?"` (question mark, still kept)

**Why nobody noticed before**: `scripts/test-conversations.js` needs to be able to reach `api.openai.com`, and this machine has long been unable to connect — this test suite **has never run**, and moreover all 20 of its cases are "the customer states a problem"; not a single one is "the customer asks a question".

**The regression net that has been added**:
- `src/app/api/admin/prompt-check` — a secret-protected OpenAI passthrough that lets the cases **run against the live environment** (live OpenAI is reachable)
- `scripts/test-prompt-loop.js` — replays the three real 10-14 calls verbatim over multiple turns
- `scripts/test-conversations.js` — new TC-Q01..Q04 (customer-question cases) + a global ban on repeating the opener + the tool simulation changed to match the real live setup + a fix for the multi-tool-call crash
- `scripts/fixtures/system-prompt-2026-09-30.md` — an archived copy of the prompt that had the bug at the time

Verification result: the new prompt run 4 rounds × 3 scenarios = **12/12 all pass**; static checks **62/62**; the old prompt reproduced the live failure completely in a single run.

### 🔴 P0 (additional finding) — The AI often does not call the `end_call` tool, so the work order ends up with no decision

This is the second defect uncovered while deep-diving the 10-14 infinite loop, and its impact is larger than the repetition.

**Symptom**: the AI finishes its closing line ("Have a good day" / "That's outside what we do ourselves") but **never calls the `end_call` tool**. With no tool call there is no outcome, so the work order can only fall back to `ai_decision="unsure"` — that is not a judgement, it is a guess.

**Why it is dangerous**:
- An urgent call (burst pipe, smell of gas) does not call `flag_urgent` + `end_call(urgent)` → **no urgent alert is triggered**, and Alex does not know he has to call back immediately
- Out-of-scope / purely informational calls land on "unsure" → Alex's queue fills up with false leads
- Without the summary line from the tool → the work order summary degrades into a generic sentence the LLM wrote on its own

**Measured**: across 27 conversation cases, the AI called `end_call` in only **15** of them. Writing "→ end_call" in the prompt does not work — this cannot be controlled by prompting.

**Fix (two legs)**:
1. **Prompt layer**: a new "Always close the call with end_call" section — saying the closing words and calling the tool must happen in the **same message**; the tool description was also changed to "Call it in the SAME message as your closing words".
2. **Code layer (the deterministic safety net)**: **tool calls are no longer the only source of the decision**.
   - `call-extraction.ts` adds `decisionSource` (`"tool"` / `"default"`)
   - `openai-summarize.ts` adds `classifyCallOutcome()` — using **exactly the same decision rules as the prompt**, so that the LLM infers the outcome from the transcript
   - `order.ts`: this fallback is only used when the AI **called none of the decision tools**; if a tool was called, the tool wins
   - `ai_decision_reason` records `inferred from transcript (the AI did not call end_call)`, so it is traceable

**Verified**: replaying the 10-14 call that did not call end_call against the live environment → the work order's `ai_decision_reason` = `inferred from transcript (the AI did not call end_call)`, and a `webhook:outcome` record appears in `llm_usage` (showing that the classification call really ran). The decisions of the two 10-29 calls that did call the tool are unaffected.

**Conclusion**: from now on **no call can end up without a decision because the model forgot to call the tool**.

## 4. One Structural Problem Still Awaiting Your Decision

**Apart from the mobile number, the customer name and callback number collected by the AI are basically not persisted in structured form.**

- Customer name: relies on the LLM guessing it out of the transcript (`customer_name_extracted`); for today's two calls it is `null` in both cases (because when the customer said "My name is Ethan", the AI's questions in the transcript were filtered out — this has been fixed along with the bug above)

**Recommendation**: add 3 optional fields to the `end_call` tool (`customer_name` / `callback_number` / `preferred_time`), filled in by the AI whenever it asks.
This changes the tool schema + the prompt + the `/api/vapi/tools` route; it is a small change to AI-visible behavior — **I will do it once you give the go-ahead**.

### 🟢 New — Automated AI behavior checkups (the concrete form of "the AI must not freak out")

In the repetition incident, **nothing abnormal was visible on the work order**: the summary only said "Customer inquired about TV mounting service",
and you would never notice it without opening the recording. So now every call gets an **automatic checkup**:

| Flag | Meaning |
|---|---|
| `repeated_turn` | the AI said the same thing twice in a row |
| `opener_echo` | the customer had already spoken and the AI still repeated the opening question |
| `no_customer_turn` | the AI said 3 or more lines and the customer never got a word in (dead line) |

- The detection logic lives in `detectAIQualityIssues()` in `src/lib/call-extraction.ts`
- It lands in `work_orders.ai_quality_flag` (migration 017)
- The dashboard list carries a red **⚠ AI misbehaved** badge, and the work order detail page explains it in a red box above the transcript
- Calls that have been flagged **are not wiped out by later reprocessing**
- The regression assertions live in `scripts/test-call-extraction.js` (218 assertions in total, all pass)

**Real-data verification**: replaying the 10-14 repetition call → `ai_quality_flag = "repeated_turn,opener_echo"`,
and **only this one call out of all 120 in the database is flagged** — the remaining 119 are all clean.

This is the real form of "the AI must not freak out": not by prayer, but by **measuring every single time**. From now on, whenever a new abnormal pattern shows up,
adding one detection rule makes it immediately visible, with no manual flipping and re-writing.
